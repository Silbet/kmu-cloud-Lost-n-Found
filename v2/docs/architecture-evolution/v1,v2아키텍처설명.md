# 아키텍처 발전 과정 발표 메모

## 발표 설명 흐름

각 단계는 다음 순서로 설명한다.

```text
1. V1에서는 어떤 구조였는지
2. 그 구조에서 어떤 문제가 있었는지
3. 왜 그 문제가 서비스 운영에 위험한지
4. V2에서 어떤 부분을 분리하거나 개선했는지
5. 그 문제를 해결하기 위해 어떤 AWS 서비스를 선택했는지
```

이번 V2 개선의 핵심은 단순히 AWS 서비스를 많이 사용하는 것이 아니다. **요구사항과 문제 상황에 맞는 클라우드 서비스를 선택해서, V1의 한계를 줄이는 것**이다.

## 전체 방향

V1은 EC2 한 대에 프론트엔드, 백엔드, DB, 이미지 저장까지 모두 올린 구조였다. 빠르게 구현하고 배포하기에는 단순했지만, 운영 관점에서는 EC2 하나가 너무 많은 책임을 가지고 있었다.

그래서 V2에서는 EC2에 묶여 있던 책임을 역할별로 분리했다. 발표에서는 각 단계마다 **무엇을 분리하거나 개선했는지**, **그게 왜 문제였는지**, **어떤 AWS 서비스로 해결했는지**를 중심으로 설명한다.

## 0. V1: EC2 단일 서버 구조

```text
사용자
  -> EC2
      - React 정적 파일
      - NestJS 백엔드
      - PostgreSQL 컨테이너
      - 업로드 이미지
```

V1은 EC2 한 대에 모든 구성요소를 올린 단일 서버 구조였다. 이 구조는 초기 개발에는 빠르고 단순하지만, EC2 장애나 재배포가 발생하면 API뿐 아니라 DB와 이미지 파일까지 함께 영향을 받을 수 있다.

즉 V1의 한계는 **EC2 하나에 실행 환경, 상태 데이터, 파일 저장, 정적 파일 제공 책임이 모두 묶여 있었다는 점**이다. V2는 이 책임들을 하나씩 분리하면서 발전했다.

## 1. 데이터 저장소 분리: EC2 내부 DB/이미지 -> RDS/S3

```text
[전] EC2 내부 PostgreSQL 컨테이너 + EC2 내부 업로드 이미지
[후] RDS PostgreSQL + S3 이미지 저장소
```

분리/개선한 부분은 EC2 내부에 있던 PostgreSQL과 업로드 이미지를 RDS와 S3로 옮긴 것이다.

이 선택이 해결한 문제는 **상태 데이터가 EC2 장애나 재배포에 같이 휘말리는 문제**다. DB와 이미지는 단순 실행 파일이 아니라 서비스의 상태를 가진 데이터다. 프론트엔드나 백엔드는 다시 배포할 수 있지만, 신고 내역, 습득물 정보, 매칭 상태, 수령 상태, 업로드 이미지는 사라지면 복구하기 어렵다.

그래서 관계형 상태 데이터는 RDS PostgreSQL로 분리하고, 계속 쌓이는 이미지 파일은 S3로 분리했다. 이를 통해 서버를 교체하거나 API 실행 환경을 바꿔도 핵심 데이터는 독립적으로 유지할 수 있다.

## 2. 정적 파일/이미지 조회 분리: EC2 직접 제공 -> CloudFront/S3

```text
[전] EC2/API 서버가 React 정적 파일과 이미지를 직접 제공
[후] S3 + CloudFront가 정적 파일과 이미지 조회 제공
```

분리/개선한 부분은 React 정적 파일과 이미지 조회를 API 서버가 직접 제공하지 않고, S3와 CloudFront를 통해 제공하도록 바꾼 것이다.

이 선택이 해결한 문제는 **API 서버가 서버 로직과 상관없는 정적 리소스 제공까지 떠안는 문제**다. React 빌드 파일과 이미지는 매번 서버가 계산해서 만드는 데이터가 아니라 반복해서 전달되는 정적 리소스다.

분실물 서비스는 목록과 검색 화면에서 이미지가 자주 반복 조회된다. 이런 트래픽까지 API 서버가 처리하면 비즈니스 로직 처리와 정적 리소스 제공 부담이 한 곳에 몰린다. 그래서 서버 로직이 필요 없는 정적 제공은 S3와 CloudFront로 분리해 API 서버의 부담을 줄였다.

## 3. 이미지 업로드 경로 변경: 백엔드 직접 업로드 -> Presigned URL

```text
[전] 브라우저 -> API 서버 -> 이미지 파일 처리 -> 저장소
[후] API 서버는 Presigned URL 발급, 브라우저는 S3로 직접 업로드
```

분리/개선한 부분은 이미지 파일을 백엔드가 직접 받지 않고, Presigned URL을 통해 브라우저가 S3로 직접 업로드하도록 바꾼 것이다.

이 선택이 해결한 문제는 **API 서버가 큰 파일 바이트를 직접 처리하면서 생기는 요청 크기, 실행 시간, 메모리 부담**이다. 분실물 신고와 습득물 등록에는 사진이 자주 포함되고, 스마트폰 사진은 용량이 클 수 있다. 이 파일을 API 서버가 직접 받으면 응답 시간이 길어지고 서버 부하도 커진다.

Presigned URL 방식에서는 API 서버가 업로드 권한만 발급한다. 실제 파일 전송은 브라우저와 S3 사이에서 이루어지므로, API 서버는 신고 데이터와 이미지 객체 키만 관리하면 된다. 이는 이후 Lambda 전환에도 더 적합한 구조다.

## 4. 백엔드 API 서버 전환: EC2 백엔드 -> API Gateway/Lambda

```text
[전] EC2에서 NestJS 백엔드 API 서버 상시 실행
[후] API Gateway -> Lambda로 요청 기반 API 처리
```

분리/개선한 부분은 EC2에서 계속 실행되던 백엔드 API 서버를 API Gateway와 Lambda 기반의 요청 기반 실행 환경으로 옮긴 것이다.

이 선택이 해결한 문제는 **API 운영이 항상 켜져 있는 EC2 서버에 계속 의존하는 문제**다. 분실물 서비스는 항상 높은 트래픽이 발생하는 서비스라기보다, 평소에는 요청이 적고 특정 기간에 사용량이 늘어나는 형태에 가깝다.

요청이 적은 시간에도 EC2를 계속 운영하면 비용과 관리 부담이 생긴다. 반대로 사용량이 늘어날 때는 서버 확장도 직접 고려해야 한다. Lambda는 요청이 들어올 때 실행되고 자동 확장이 가능하므로, 이런 사용 패턴에 맞다.

다만 API 서버가 EC2 내부 DB나 파일 시스템에 의존한 상태라면 Lambda 전환이 어렵다. 그래서 먼저 RDS, S3, CloudFront, Presigned URL로 의존성을 줄인 뒤 API 실행 환경을 Lambda로 전환했다.

## 5. 매칭 처리 분리: API 내부 동기 처리 -> SQS/Worker Lambda

```text
[전] API Lambda 안에서 매칭까지 동기 처리
[후] API Lambda -> SQS -> Matching Worker Lambda -> DLQ
```

분리/개선한 부분은 신고 등록 API 안에서 매칭을 동기적으로 처리하던 흐름을 SQS와 Matching Worker Lambda로 분리한 것이다.

이 선택이 해결한 문제는 **매칭 처리 때문에 API 응답이 늦어지고, 매칭 실패가 신고 등록 흐름까지 흔들 수 있는 문제**다. 사용자가 가장 먼저 기대하는 것은 신고가 정상 접수되는 것이다. 매칭 결과는 즉시 화면에 보여주지 않아도 되고, 나중에 알림으로 알려줘도 된다.

그런데 매칭을 같은 API 요청 안에서 처리하면 매칭이 느려질 때 신고 등록 응답도 늦어진다. 매칭 로직 오류나 DB 일시 장애가 발생하면 신고 등록 자체가 실패한 것처럼 보일 수도 있다.

그래서 API는 신고 등록을 먼저 완료하고, 매칭 작업은 SQS에 메시지로 넘긴다. Worker Lambda가 큐를 읽어 매칭을 처리하고, 실패한 메시지는 DLQ에서 추적하거나 재처리할 수 있다. 즉 SQS는 단순한 성능 개선이 아니라 **응답 흐름과 핵심 비즈니스 작업의 실패 범위를 분리하기 위한 선택**이다.

## 6. 후처리/알림/예약 작업 분리: API 내부 처리 -> 이벤트 기반 작업

```text
[전] API 서버 내부에서 이미지 후처리, 알림, 예약 작업 처리
[후] S3 Event -> 이미지 후처리 Lambda
[후] SNS Topic -> 알림 발행 지점 분리
[후] EventBridge Scheduler -> Scheduled Jobs Lambda
```

분리/개선한 부분은 이미지 후처리, 알림 발행, 예약 작업을 API 서버 내부 처리에서 이벤트 기반 작업으로 분리한 것이다.

이 선택이 해결한 문제는 **사용자 요청과 직접 관련 없는 후처리 작업이 API 응답 시간과 서버 책임을 늘리는 문제**다. 이미지 변환, 알림 발행, 장기 미수령 처리 같은 작업은 사용자의 요청에 즉시 응답하기 위한 핵심 흐름과 분리할 수 있다.

이미지 후처리는 S3 업로드 이벤트로 실행한다. 이렇게 하면 원본 업로드 이후 별도 Lambda가 썸네일이나 최적화 이미지를 만들고, API 서버는 이미지 변환 책임에서 벗어난다.

알림은 SNS Topic으로 발행 지점을 분리했다. 현재 단계에서 외부 알림 기능을 완성했다는 의미보다는, API 서버가 이메일, SMS, 푸시 같은 채널을 직접 알지 않아도 되도록 확장 구조를 마련한 것이다.

시간 기반 작업은 EventBridge Scheduler로 분리했다. 장기 미수령 처리나 자동 취소 같은 작업은 API 요청이 들어왔을 때만 실행되면 안 된다. EventBridge Scheduler를 사용하면 특정 EC2 서버의 실행 상태에 의존하지 않고 정해진 시간에 작업을 실행할 수 있다.

## 최종 정리

V2의 개선은 다음 기준으로 진행했다.

```text
1. 상태 데이터 분리
   -> EC2 장애/재배포가 데이터 손실로 이어질 수 있는 문제 해결

2. 정적 제공 분리
   -> API 서버가 정적 파일과 이미지 조회까지 처리하는 문제 해결

3. 업로드 경로 분리
   -> 큰 이미지 파일 처리로 인한 API 서버 부하 해결

4. API 실행 환경 전환
   -> 항상 켜진 EC2 서버에 API 운영이 의존하는 문제 해결

5. 매칭 처리 비동기화
   -> API 응답 지연, 매칭 실패 추적 어려움 해결

6. 후처리/알림/예약 작업 분리
   -> API 응답 흐름이 부가 작업에 묶이는 문제 해결
```

결론적으로 V2는 새로운 서비스를 많이 붙인 구조가 아니라, **V1의 한계를 기준으로 문제 해결에 적합한 클라우드 서비스를 선택하고 적용한 구조**다.

```text
정적 화면 제공: S3 + CloudFront
이미지 저장/조회: S3 + CloudFront
이미지 업로드: Presigned URL
API 처리: API Gateway + Lambda
데이터 저장: RDS PostgreSQL
매칭 처리: SQS + Matching Worker Lambda + DLQ
이미지 후처리: S3 Event + Thumbnail Worker Lambda
알림 확장: SNS Topic
시간 기반 작업: EventBridge Scheduler + Scheduled Jobs Lambda
```
