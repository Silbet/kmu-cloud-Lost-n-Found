# 아키텍처 발전 과정 발표 메모

## 전체 방향

V1은 EC2 한 대에 프론트엔드, 백엔드, DB, 이미지 저장까지 모두 올린 최소 인프라 구조였다. 빠르게 배포하고 기능을 확인하기에는 적합했지만, 서비스가 실제로 운영된다고 보면 서버 장애, 재배포, 파일 저장, 매칭 처리, 이미지 조회 같은 부분이 모두 한 곳에 묶여 있다는 한계가 있었다.

V2에서는 단순히 AWS 서비스를 많이 붙이는 것이 아니라, V1에서 문제가 될 수 있는 부분을 기준으로 하나씩 분리했다. 기준은 다음과 같다.

- 사라지면 안 되는 데이터부터 분리한다.
- 서버 로직이 필요 없는 정적 제공은 CDN/S3로 뺀다.
- API 서버가 파일 바이트를 직접 다루지 않게 한다.
- API 실행 환경은 요청 기반으로 전환한다.
- 사용자 응답과 분리 가능한 핵심 작업은 큐로 분리한다.
- 후처리, 알림, 예약 작업은 사용자 요청 흐름 밖으로 분리한다.

한 문장으로 정리하면, **EC2 하나에 묶여 있던 의존성을 위험한 것부터 하나씩 끊어낸 구조**다.

## 0. V1: EC2 단일 서버 구조

```text
사용자
  -> EC2
      - React 정적 파일
      - NestJS 백엔드
      - PostgreSQL 컨테이너
      - 업로드 이미지
```

V1은 과제용 최소 인프라로 EC2 한 대에 모든 구성요소를 올린 구조다. 처음 구현과 배포가 단순하다는 장점이 있지만, 프론트, 백엔드, DB, 이미지 파일이 모두 같은 서버에 있으므로 EC2 장애나 재배포가 전체 서비스에 영향을 줄 수 있다.

이 구조는 시작점으로는 합리적이지만, 분실물 서비스처럼 이미지와 상태 데이터가 계속 쌓이는 서비스에는 장기적으로 부담이 있다.

## 1. 데이터 저장소 분리: EC2 내부 DB/이미지 -> RDS/S3

```text
DB / 이미지 저장소 분리
```

이걸 먼저 하는 이유는 간단하다. **상태를 가진 데이터가 제일 위험하기 때문이다.**

프론트나 백엔드는 다시 빌드해서 올리면 되지만, DB 데이터나 이미지가 사라지면 복구가 어렵다. V1은 EC2 안에 PostgreSQL 컨테이너와 업로드 이미지가 같이 있어서 EC2 장애, 재배포, 서버 교체가 데이터에 영향을 줄 수 있었다.

그래서 첫 개선은 "서버를 멋있게 바꾸자"가 아니라, **사라지면 안 되는 데이터를 EC2 밖으로 빼자**였다.

### 서비스 관점의 선택 근거

분실물 서비스의 핵심 데이터는 신고 내역, 습득물, 매칭 상태, 수령 상태, 이미지다. 사용자가 물건을 찾는 과정은 이 데이터가 유지된다는 전제 위에서 동작한다. 따라서 DB는 RDS로, 이미지는 S3로 분리하는 것이 서비스 성격에 맞다.

특히 이미지는 시간이 지날수록 계속 쌓이고, 서버 디스크에 둘 경우 확장과 백업이 어려워진다. S3는 파일 저장소 역할에 맞고, RDS는 관계형 데이터와 상태 흐름 관리에 적합하다.

## 2. 정적 파일/이미지 조회 분리: EC2 직접 제공 -> CloudFront/S3

```text
Frontend S3 + CloudFront
Image S3 + CloudFront
```

데이터를 분리한 다음에는 사용자에게 자주 전달되는 정적 리소스를 분리하는 것이 자연스럽다.

프론트 React 빌드 파일은 매 요청마다 백엔드가 계산해서 주는 것이 아니라 정적 파일이다. 이미지도 분실물 목록에서 반복 조회된다. 그러면 API 서버가 굳이 화면 파일과 이미지까지 직접 줄 필요가 없다.

이 단계의 기준은 **자주 조회되지만 서버 로직이 필요 없는 것은 CDN/S3로 빼자**다.

### 서비스 관점의 선택 근거

분실물 서비스는 검색과 목록 조회가 많다. 사용자는 여러 분실물과 습득물 카드를 훑어보며 이미지를 반복해서 확인한다. 같은 이미지가 여러 사용자에게 반복 조회될 수 있으므로 CloudFront 캐싱이 잘 맞는다.

프론트엔드는 React SPA이기 때문에 정적 파일 배포에 S3와 CloudFront가 적합하고, 이미지는 `/images/*` 경로로 CloudFront를 통해 제공하면 목록과 상세 화면의 로딩을 안정화할 수 있다.

## 3. 이미지 업로드 경로 변경: 백엔드 직접 업로드 -> Presigned URL

```text
브라우저 -> S3 직접 업로드
```

이건 Lambda 전환 전에 필요한 준비 작업이다.

이미지 업로드를 백엔드가 직접 받는 상태로 Lambda에 올리면 요청 크기, 실행 시간, 메모리, 파일 처리 책임이 전부 API Lambda로 넘어간다.

그래서 API 서버를 Lambda로 바꾸기 전에 **백엔드가 파일 바이트를 직접 다루지 않게 만들자**는 개선이 필요했다.

### 서비스 관점의 선택 근거

분실물 신고와 습득물 등록에는 사진이 자주 포함된다. 실제 스마트폰 사진은 1~3MB 이상일 수 있고, 원본 해상도도 크다. 이런 파일을 API 서버가 직접 받으면 서버 부하가 커지고, 요청 처리 시간이 길어질 수 있다.

Presigned URL 방식은 API 서버가 업로드 권한만 발급하고, 브라우저가 S3로 직접 업로드하게 한다. 따라서 API 서버는 신고 데이터와 이미지 객체 키만 관리하면 되고, 파일 전송 부담은 S3가 담당한다.

## 4. 백엔드 API 서버 전환: EC2 백엔드 -> API Gateway/Lambda

```text
API Gateway + Lambda
```

처음부터 API를 Lambda로 옮기지 않은 이유는 V1 상태 그대로는 API 서버가 너무 많은 것에 의존하고 있었기 때문이다.

V1 API 서버는 프론트 정적 파일 제공, DB 연결, 이미지 파일 처리, 비즈니스 로직을 모두 들고 있었다. 그래서 먼저 DB, 이미지 저장소, 정적 파일을 분리한 뒤에 API 서버를 Lambda로 옮기는 것이 맞다.

발표용으로는 이렇게 말할 수 있다.

> API 서버를 서버리스로 전환하기 전에, 파일 시스템과 EC2 내부 DB에 대한 의존성을 먼저 제거했습니다. 그래서 Lambda 전환은 저장소 분리 이후 단계로 배치했습니다.

### 서비스 관점의 선택 근거

분실물 서비스는 항상 높은 트래픽이 발생하는 서비스라기보다, 평소에는 적당한 요청이 있다가 축제 기간, 시험 기간, 학기 초처럼 특정 시기에 사용량이 늘어날 수 있는 서비스다. 반대로 방학이나 야간에는 사용량이 매우 줄어들지만, 검색이나 신고처럼 아주 적은 요청은 계속 들어올 수 있다.

이런 특성에서는 서버가 완전히 없어지면 안 되지만, 그렇다고 EC2나 ECS Fargate처럼 항상 실행 중인 서버를 계속 유지하는 것도 비효율적일 수 있다. Lambda는 100% 요청 기반으로 실행되므로 사용량이 거의 없는 시간대에는 비용과 운영 부담을 줄이고, 요청이 들어오면 API를 계속 제공할 수 있다.

즉 이 서비스는 "항상 켜져 있어야 하지만 항상 바쁜 서비스는 아닌" 형태에 가깝기 때문에, 요청 기반 실행과 자동 확장이 가능한 Lambda가 잘 맞는다.

다만 API 서버가 파일 저장이나 EC2 내부 DB에 의존한 상태라면 Lambda 전환이 어렵다. 그래서 저장소를 먼저 분리한 뒤 API 실행 환경을 바꾸는 순서가 자연스럽다.

## 5. 매칭 처리 분리: API 내부 동기 처리 -> SQS/Worker Lambda

```text
API Lambda -> SQS -> Matching Worker Lambda
```

매칭은 API 서버가 있어야 발생하는 작업이다. 신고 등록, 신고 수정, 습득물 보관 처리 같은 API 흐름이 먼저 정리되어야 매칭 작업을 큐로 뺄 수 있다.

그리고 이 단계는 단순한 성능 개선이 아니라 서비스 흐름 개선이다.

우리 서비스에서 중요한 조건은 다음과 같았다.

> 신고 등록은 성공해야 하고, 매칭은 나중에 알림으로 알려줘도 된다.

그래서 매칭은 사용자 응답에서 분리하기 좋았고, 실패하면 DLQ로 남겨 추적할 수 있게 했다.

이 단계의 기준은 **사용자 응답과 반드시 같이 끝날 필요 없는 핵심 작업은 큐로 분리하자**다.

### 서비스 관점의 선택 근거

분실물 서비스에서 사용자가 가장 먼저 기대하는 것은 신고가 정상 접수되는 것이다. 매칭 결과는 즉시 화면에 보여주지 않아도 되고, 새 후보가 생기면 알림으로 알려주면 충분하다.

SQS로 분리하면서 얻는 이점은 단순히 "응답이 빨라진다"만이 아니다.

- 등록 API와 매칭 연산의 실패 범위를 분리할 수 있다.
- 축제 기간처럼 신고/습득물 등록이 몰릴 때 매칭 작업을 큐에 쌓아두고 순차적으로 처리할 수 있다.
- API Lambda와 Matching Worker Lambda의 확장 기준을 다르게 가져갈 수 있다.
- 매칭 로직 오류나 DB 일시 장애가 발생해도 실패 메시지를 DLQ에서 확인할 수 있다.
- 향후 AI 매칭이나 이미지 기반 매칭처럼 더 무거운 작업으로 확장하더라도 API 응답 흐름을 크게 바꾸지 않아도 된다.

다만 현재 단순 문자열 기반 매칭만 놓고 보면 SQS가 반드시 필요한 것은 아닐 수 있다. 작은 MVP라면 API 안에서 동기 처리해도 동작한다. 하지만 이 프로젝트에서는 매칭을 서비스 핵심 기능으로 보고, "신고 접수는 성공해야 하며 매칭은 실패 추적과 재처리가 가능해야 한다"는 조건을 더 중요하게 보았다.

따라서 SQS는 단순히 트래픽이 커서 넣은 것이 아니라, **사용자 요청 흐름과 핵심 비즈니스 작업을 분리하고 실패를 관리하기 위한 선택**으로 설명하는 것이 맞다.

## 6. 후처리/알림/예약 작업 분리: API 내부 처리 -> 이벤트 기반 작업

```text
S3 Event -> 이미지 후처리 Lambda
SNS Topic
EventBridge Scheduler -> Scheduled Jobs Lambda
```

이 단계들은 핵심 요청 경로가 먼저 정리된 뒤에 붙이는 것이 인프라적으로 자연스럽다. V1에서도 EC2 백엔드 안에서 이미지 변환, 알림 생성, 장기 미수령 조회를 구현할 수 있다. V2의 핵심은 같은 기능을 하더라도 **사용자 요청과 직접 관련 없는 작업을 API 서버 책임에서 분리했다**는 점이다.

이미지 후처리는 S3 원본 업로드 경로가 있어야 이벤트 기반으로 분리할 수 있다. 알림 발행은 API 서버의 상태 변경 흐름이 정리되어야 발행 지점을 명확히 둘 수 있다. 스케줄 작업은 RDS에 저장된 상태 데이터를 기준으로 별도 Lambda가 주기적으로 조회하는 구조이므로, DB와 API 흐름이 먼저 안정된 뒤 붙이는 편이 안전하다.

그래서 이들은 핵심 API 요청 경로를 먼저 만든 뒤, 그 주변에서 발생하는 후처리성 작업으로 분리하는 것이 맞다.

이 단계의 기준은 **핵심 요청 흐름이 안정된 뒤, 사용자 요청과 무관한 후처리/알림/예약 작업을 분리하자**다.

### 서비스 관점의 선택 근거

분실물 목록에서는 여러 이미지를 한 번에 보여준다. 원본 이미지를 그대로 보여주면 로딩이 느려지고 모바일 데이터 사용량도 커진다. 그래서 S3에 원본이 올라오면 Lambda가 목록용 썸네일과 상세용 이미지를 생성하도록 했다. 원본은 보관하고, 사용자 화면에는 최적화된 이미지를 제공하는 방식이다.

이 작업은 EC2 백엔드나 API Lambda 안에서도 할 수 있지만, 이미지 변환은 파일 업로드 이후 발생하는 독립적인 후처리 작업이다. API 요청 안에서 같이 처리하면 신고 등록이나 업로드 흐름이 이미지 변환 시간에 영향을 받을 수 있다. S3 Event와 별도 Lambda로 분리하면 원본 업로드 이후 자동으로 실행되고, API 서버는 이미지 변환 책임에서 벗어난다.

알림은 V1에서도 인앱 알림 테이블에 저장하는 방식으로 구현할 수 있다. V2에서 SNS Topic을 둔 이유는 알림 생성 로직을 외부 채널 확장 가능성과 분리하기 위해서다. API 서버가 이메일, SMS, 푸시 같은 채널을 직접 알 필요 없이 알림 이벤트를 발행하고, 이후 구독 채널을 붙일 수 있다.

다만 현재 구현은 실제 외부 발송까지 완성한 것이 아니라 SNS Topic publish 연결을 확인한 단계다. 따라서 발표에서는 "외부 알림 기능을 완성했다"가 아니라, **알림 발행 지점을 SNS Topic으로 분리해 외부 채널 확장 구조를 마련했다**고 말하는 것이 정확하다.

장기 미수령 처리나 자동 취소 같은 작업은 API 요청이 들어왔을 때만 실행되면 안 된다. EC2에서 cron으로 돌릴 수도 있지만, 그러면 다시 특정 서버의 실행 상태에 의존하게 된다. EventBridge Scheduler는 시간 기반 실행 책임을 AWS 관리형 서비스로 분리하고, Scheduled Jobs Lambda는 해당 시간에 필요한 조회와 상태 처리를 담당한다.

다만 현재 발표에서는 이 부분을 "완성된 자동 폐기 기능"처럼 말하기보다, **시간 기반 작업을 API 요청 흐름과 서버 접속 여부에서 분리하는 구조**로 설명하는 것이 맞다.

## 최종 정리

V2의 발전 순서는 다음과 같다.

```text
1. 먼저, 잃으면 안 되는 데이터부터 EC2 밖으로 분리
2. 다음, 서버 로직이 필요 없는 정적 제공 책임 분리
3. 그다음, API 서버가 파일 바이트를 직접 다루지 않게 개선
4. 이후, API 서버를 서버리스로 전환
5. 그리고, 응답과 분리 가능한 핵심 작업인 매칭을 비동기화
6. 마지막으로, 후처리/알림/시간 기반 작업을 분리
```

이 순서는 기술을 많이 붙인 순서가 아니라, **EC2에 묶여 있던 의존성을 위험한 것부터 하나씩 끊는 순서**다.

최종적으로 V2는 다음처럼 역할이 나뉜다.

```text
정적 화면 제공: S3 + CloudFront
이미지 저장/조회: S3 + CloudFront
이미지 업로드: Presigned URL
API 처리: API Gateway + Lambda
데이터 저장: RDS PostgreSQL
매칭 처리: SQS + Matching Worker Lambda + DLQ
이미지 후처리: S3 Event + Thumbnail Worker Lambda
알림 확장: SNS Topic
시간 기반 작업: EventBridge Scheduler + Scheduled Jobs Lambda
```
