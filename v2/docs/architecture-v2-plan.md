# Version 2. 클라우드 서비스 기반 아키텍처 개선 계획

## 1. 개선 목표

V2는 V1에서 발견한 한계와 문제를 바탕으로 클라우드 서비스를 활용해 아키텍처를 개선하는 버전이다. 단순히 AWS 서비스를 많이 사용하는 것이 아니라, 현재 구조의 문제를 해결하는 데 필요한 서비스를 선택하고 각 선택이 어떤 문제를 해결하는지 설명하는 것을 목표로 한다.

V2의 핵심 방향은 EC2 단일 서버 중심 구조에서 벗어나 데이터베이스, 정적 파일, 이미지 저장소, 비동기 작업, 자동 실행 작업을 각각 적절한 관리형 서비스로 분리하는 것이다.

## 2. V2 전체 방향

- API 서버는 API Gateway + Lambda 기반으로 전환한다.
- DB는 EC2 또는 Docker 볼륨에서 분리해 RDS PostgreSQL로 이전한다.
- React 정적 파일은 S3 + CloudFront로 분리 배포한다.
- 이미지 파일은 S3에 저장하고, 업로드는 Presigned URL 방식으로 개선한다.
- 무거운 매칭 처리는 SQS + Lambda 기반 비동기 처리로 분리한다.
- 썸네일 생성은 S3 Event + Lambda로 자동화한다.
- 알림 채널은 SNS 기반 확장을 검토한다.
- 자동 실행 작업은 서비스 코드 구현 이후 EventBridge Scheduler + Lambda로 분리한다.

## 3. 구현 우선순위

### 1순위. DB 분리 - RDS PostgreSQL

#### 왜 필요한가

V1에서는 PostgreSQL이 EC2 또는 EC2 내부 Docker 볼륨에 함께 구성되어 있어 애플리케이션 서버 장애, 재배포, 서버 교체가 DB 데이터에 영향을 줄 수 있다. 또한 백업, 복구, 디스크 관리 책임이 서버 운영에 묶여 있어 안정성이 낮다.

#### 어떻게 개선하는가

PostgreSQL을 RDS로 이전해 애플리케이션 서버와 DB를 분리한다. 백엔드는 환경변수로 RDS 엔드포인트를 바라보도록 변경하고, 기존 Prisma 마이그레이션을 RDS에 적용한다.

Aurora Serverless v2도 대안이 될 수 있지만, 현재 성북구 7개 대학 분실물 시스템 규모에서는 비용 대비 효용을 별도로 검토한 결과 RDS PostgreSQL을 우선 선택한다. 자세한 판단 근거는 문서 하단의 부록 A를 참고한다.

#### 이 순서로 하는 이유

DB는 모든 API 기능의 기반이다. RDS로 먼저 분리해야 이후 API Gateway + Lambda 전환, EC2 제거, 서버 교체 작업을 데이터 유실 위험 없이 진행할 수 있다.

#### 해결되는 문제

- EC2 장애와 DB 장애 범위 분리
- 서버 재배포와 데이터 저장소 분리
- 자동 백업과 복구 기반 확보
- Lambda API 전환을 위한 DB 접속 대상 명확화

#### 구현 시 고려사항

- RDS 보안 그룹과 Lambda 접근 경로
- DB 접속 환경변수 관리
- Prisma 마이그레이션 적용 방식
- 백업 보존 기간과 복구 전략

### 2순위. 이미지 저장소 이전 - S3

#### 왜 필요한가

V1에서는 업로드 이미지가 EC2 디스크 또는 Docker 볼륨에 저장될 수 있어 EC2 장애, 디스크 부족, 서버 확장 시 이미지 유실 문제가 발생할 수 있다.

#### 어떻게 개선하는가

분실물, 습득물, 신고 사진을 S3 버킷에 저장한다. DB에는 파일 자체가 아니라 S3 객체 키와 접근 URL에 필요한 메타데이터를 저장한다.

#### 이 순서로 하는 이유

이미지 저장소를 먼저 분리해야 API 서버를 Lambda로 전환할 때 파일 시스템 의존성을 제거할 수 있다. Lambda는 로컬 디스크를 영구 저장소로 사용할 수 없기 때문에 S3 분리가 선행되어야 한다.

#### 해결되는 문제

- EC2 디스크 의존 제거
- 이미지 데이터 유실 위험 감소
- 서버 확장 시 공통 이미지 저장소 확보
- 장기 보관과 접근 제어 기반 확보

#### 구현 시 고려사항

- S3 버킷 구조와 객체 키 규칙
- 원본 이미지 공개 여부
- 파일 삭제 정책
- 개인정보 또는 민감 이미지 접근 제어

### 3순위. 이미지 업로드 경로 개선 - Presigned URL

#### 왜 필요한가

V1에서는 이미지 업로드가 백엔드 서버를 거쳐 처리되므로 서버 CPU, 메모리, 네트워크 부담이 커진다. 특히 Lambda API로 전환할 경우 큰 파일 업로드를 API가 직접 처리하면 실행 시간과 요청 크기 제한 문제가 생길 수 있다.

#### 어떻게 개선하는가

백엔드는 S3 Presigned URL을 발급하고, 클라이언트는 해당 URL로 S3에 직접 업로드한다. 백엔드는 업로드 완료 후 파일 메타데이터만 저장한다.

#### 이 순서로 하는 이유

S3 저장소 이전 이후에 자연스럽게 적용할 수 있는 개선이다. 이 단계를 마치면 API 서버는 파일 바이트를 직접 다루지 않게 되어 Lambda 전환 부담이 줄어든다.

#### 해결되는 문제

- 백엔드 서버의 파일 업로드 부하 감소
- Lambda 요청 크기와 실행 시간 부담 감소
- 이미지 저장 책임을 S3로 명확히 분리

#### 구현 시 고려사항

- Presigned URL 만료 시간
- 업로드 가능한 파일 크기와 확장자 제한
- 업로드 완료 검증 방식
- 실패한 업로드 객체 정리 정책

### 4순위. 정적 파일 배포 분리 - S3 + CloudFront

#### 왜 필요한가

V1에서는 NestJS 백엔드 또는 EC2가 React 빌드 파일까지 함께 서빙해 API 서버가 정적 파일 트래픽도 부담한다. 백엔드 장애가 프론트 화면 접근 불가로 이어질 수 있다.

#### 어떻게 개선하는가

React 빌드 결과물을 S3에 업로드하고 CloudFront를 통해 사용자에게 제공한다. API 서버는 데이터 처리만 담당하고, 프론트 정적 리소스 배포는 별도 경로로 분리한다.

#### 이 순서로 하는 이유

DB와 이미지 저장소 분리 이후 프론트 배포를 분리하면 서버리스 API 전환 전에도 사용자 화면과 API 서버 책임을 명확히 나눌 수 있다.

#### 해결되는 문제

- API 서버의 정적 파일 트래픽 부담 감소
- CloudFront 캐싱을 통한 응답 속도 개선
- 백엔드 장애 시에도 최소 안내 화면 제공 가능
- 프론트와 백엔드 배포 독립성 확보

#### 구현 시 고려사항

- CloudFront 캐시 무효화 전략
- API 엔드포인트 환경변수 주입 방식
- SPA 라우팅을 위한 오류 응답 설정
- HTTPS 인증서와 도메인 연결

### 5순위. API 서버 서버리스 전환 - API Gateway + Lambda

#### 왜 필요한가

V1은 EC2 한 대에 API 서버가 의존하므로 해당 인스턴스 장애 시 전체 API가 중단된다. 사용량이 낮은 기간과 높은 기간의 차이가 큰 서비스 특성상 요청 기반 실행과 자동 확장이 가능한 구조가 적합하다.

#### 어떻게 개선하는가

API Gateway를 외부 진입점으로 두고 Lambda가 API 요청을 처리하도록 전환한다. 기존 NestJS 구조를 Lambda에 올리는 방식과 기능별 Lambda로 분리하는 방식을 비교해 적용 범위를 결정한다.

#### 이 순서로 하는 이유

DB, 이미지 저장소, 정적 파일 배포가 먼저 분리되어야 API 서버가 파일 시스템과 EC2 상태에 덜 의존한다. 기반 의존성을 제거한 뒤 Lambda로 옮기는 것이 전환 위험이 낮다.

#### 해결되는 문제

- EC2 단일 장애점 완화
- 요청량 변화에 따른 자동 확장
- 유휴 시간 비용 절감 가능
- API와 정적 파일 배포 책임 분리

#### 구현 시 고려사항

- Cold start 지연
- RDS connection 관리
- RDS Proxy 도입 여부
- Lambda 패키징과 배포 방식
- NestJS 전체 Lambda와 기능별 Lambda 중 선택

### 6순위. 매칭 처리 비동기화 - SQS + Lambda

#### 왜 필요한가

V1에서는 분실물 또는 습득물 등록 시 매칭 검사를 동기로 수행해 API 응답이 느려질 수 있다. 매칭 결과는 등록 응답에 반드시 포함될 필요가 없으므로 사용자 요청 흐름과 분리할 수 있다.

#### 어떻게 개선하는가

등록 API는 데이터를 저장한 뒤 매칭 작업 메시지를 SQS에 적재하고 빠르게 응답한다. Lambda는 큐를 소비하면서 매칭을 수행하고 결과를 DB에 저장한다. 매칭 작업 큐에는 DLQ를 연결해 같은 메시지가 반복 실패할 경우 `pj-kmucloud-6-v2-matching-dlq`로 이동시킨다.

#### 이 순서로 하는 이유

API 서버가 Lambda로 전환된 이후 무거운 연산을 별도 Lambda 작업으로 분리하면 요청 응답 Lambda와 작업 처리 Lambda의 책임이 명확해진다.

#### 해결되는 문제

- 등록 API 응답 속도 개선
- 사용자 요청과 무거운 매칭 연산의 리소스 경쟁 감소
- 매칭 작업 재시도와 실패 처리 기반 확보

#### 구현 시 고려사항

- SQS 메시지 구조
- 중복 처리 방지
- 실패 메시지와 DLQ 구성: `pj-kmucloud-6-v2-matching-queue`에 `pj-kmucloud-6-v2-matching-dlq`를 연결하고, 3~5회 실패 후 이동하도록 설정
- 매칭 결과 저장 후 사용자에게 알림을 보내는 흐름

### 7순위. 썸네일 생성 자동화 - S3 Event + Lambda

#### 왜 필요한가

업로드 원본 이미지는 보통 용량이 크기 때문에 목록 화면에서 여러 이미지를 동시에 조회하면 로딩 지연, 모바일 데이터 사용량 증가, 전송 비용 증가 문제가 발생한다.

#### 어떻게 개선하는가

원본 이미지가 S3에 업로드되면 S3 Event가 Lambda를 실행하고, Lambda가 가로 480px WebP 형식의 목록 조회용 썸네일과 가로 1600px WebP 형식의 상세용 이미지를 생성해 별도 경로에 저장한다. 목록과 매칭 후보 카드에서는 썸네일을 사용하고, 상세 화면에서는 상세용 이미지를 사용한다. 원본 이미지는 재처리와 관리자 확인을 위해 비공개로 보관하며 일반 사용자 화면에는 직접 제공하지 않는다.

썸네일 생성 과정에서는 촬영 기기, 촬영 시간 등 원본 JPEG에 포함될 수 있는 EXIF 메타데이터를 결과 WebP에 포함하지 않는다. 원본은 접근을 제한해 보관하고, 일반 목록 화면에는 EXIF가 제거된 썸네일을 제공해 불필요한 개인정보 노출 가능성을 줄인다.

실제 Galaxy S25로 촬영한 `4000x3000`, 약 3.23 MB JPEG 사진을 배포된 Lambda에서 처리한 결과는 다음과 같다.

| 항목 | 원본 | 썸네일 |
| --- | ---: | ---: |
| 해상도 | 4000x3000 | 480x360 |
| 파일 형식 | JPEG | WebP |
| 파일 크기 | 3,229,872 bytes | 36,986 bytes |

실측 결과 파일 크기는 약 98.85% 감소해 원본보다 약 87.3배 작아졌으며, 실제 이미지 처리 시간은 약 759ms였다. 사진의 장면 복잡도, 노이즈, 원본 압축률에 따라 결과 크기와 처리 시간은 달라질 수 있으므로 이 수치는 보장값이 아닌 대표 측정 사례다. 다만 일반적인 12MP 카메라 사진을 가로 480px WebP로 축소하면 목록 화면의 이미지 전송량을 크게 줄이는 효과를 기대할 수 있다.

동일한 실제 사진으로 목록용 이미지와 상세용 이미지를 함께 생성하도록 확장한 결과, 목록용 이미지는 `480x360`, 약 37 KB였고 상세용 이미지는 `1600x1200`, 약 306 KB였다. 두 이미지를 함께 생성하는 데 약 2.0초가 걸렸고 최대 메모리 사용량은 172 MB였다. 두 변환 이미지 모두 EXIF 메타데이터를 포함하지 않았다.

#### 이 순서로 하는 이유

S3 이미지 저장과 Presigned URL 업로드가 먼저 적용되어야 S3 업로드 이벤트를 기반으로 썸네일 생성을 자동화할 수 있다.

#### 해결되는 문제

- 목록 화면 이미지 전송량 감소
- 모바일 사용자 로딩 속도 개선
- 원본 이미지와 표시용 이미지 역할 분리
- 목록 응답에서 촬영 기기와 촬영 시간 같은 EXIF 메타데이터 노출 방지

#### 구현 시 고려사항

- 썸네일 크기와 품질
- 원본과 썸네일 객체 키 매핑
- 목록에서는 썸네일, 상세 화면에서는 상세용 이미지를 선택하는 API 응답 및 프론트엔드 처리
- 원본 이미지 접근 권한 제한과 EXIF 메타데이터 보존 정책
- 이미지 처리 실패 시 재시도
- 기존 이미지에 대한 일괄 썸네일 생성

### 8순위. 알림 채널 확장 - SNS

#### 왜 필요한가

V1의 알림은 인앱 중심이므로 사용자가 페이지를 열지 않으면 중요한 알림을 확인하기 어렵다. 매칭, 보관, 수령 일정과 같은 이벤트는 외부 채널로 확장할 필요가 있다.

#### 어떻게 개선하는가

알림 발송 책임을 분리하고 SNS를 통해 이메일, SMS, 푸시 등 외부 채널 확장을 검토한다. 초기에는 비용과 개인정보 동의를 고려해 적용 채널을 제한할 수 있다.

#### 이 순서로 하는 이유

알림은 매칭 비동기화 이후 효과가 커진다. 매칭 결과가 백그라운드에서 생성되면 사용자에게 결과를 전달할 외부 채널이 필요해진다.

#### 해결되는 문제

- 사용자 접속 여부와 무관한 알림 가능
- 매칭 결과 전달성 개선
- 향후 여러 알림 채널로 확장 가능

#### 구현 시 고려사항

- 실제 사용할 채널 선택
- 개인정보 수집과 알림 수신 동의
- 발송 비용
- 알림 실패 처리와 재시도

### 9순위. 자동 실행 분리 - EventBridge Scheduler + Lambda

#### 왜 필요한가

폐기, 자동 취소, 상태 변경과 같은 시간 기반 규칙이 사용자 브라우저 접속 여부에 의존하면 안정적으로 실행되지 않는다. 자동 실행 작업은 사용자 요청 흐름과 독립적으로 서버 측에서 실행되어야 한다.

#### 어떻게 개선하는가

EventBridge Scheduler가 정해진 시간에 Lambda를 실행하고, Lambda가 폐기 대상 확인, 자동 취소, 상태 변경 같은 배치 작업을 수행한다.

#### 이 순서로 하는 이유

현재 자동 실행 대상 서비스 코드가 아직 구현되지 않았기 때문에 우선순위를 뒤로 둔다. 핵심 저장소, API, 비동기 처리 구조를 먼저 안정화한 뒤 정책 기반 자동 실행을 붙이는 것이 자연스럽다.

#### 해결되는 문제

- 사용자 접속 여부와 무관한 시간 기반 처리
- 브라우저 의존 로직 제거
- 배치 작업 실행 이력과 실패 추적 가능

#### 구현 시 고려사항

- 자동 실행 대상 정책 확정
- 실행 주기
- 중복 실행 방지
- 실패 알림과 로그 모니터링

## 4. 이후 논의할 결정 사항

- NestJS 전체를 Lambda로 올릴지, 기능별 Lambda로 나눌지 결정한다.
- RDS connection 관리를 위해 RDS Proxy를 도입할지 결정한다.
- 이미지 접근 권한을 공개 URL, CloudFront signed URL, 백엔드 프록시 중 어떤 방식으로 처리할지 결정한다.
- SNS 기반 알림에서 실제 적용할 채널을 결정한다.
- 자동 실행 작업의 정책과 실행 주기를 서비스 코드 구현 후 확정한다.

## 부록 A. DB 선택 근거 - RDS PostgreSQL과 Aurora Serverless v2 비교

### 전제

이 서비스는 성북구 내 7개 대학에서 공동으로 사용하는 분실물 시스템을 가정한다. 서비스 특성상 SQL 기반의 관계형 데이터 모델이 필요하다. 사용자, 학교, 분실물, 습득물, 이미지 메타데이터, 보관 장소, 상태 변경 이력, 문의 또는 매칭 결과처럼 서로 관계가 있는 데이터를 다루므로 DynamoDB 같은 NoSQL 저장소는 이번 비교 대상에서 제외한다.

잠재 사용자는 7개 대학의 학생과 교직원을 합쳐 약 8만~11만 명 수준으로 볼 수 있다. 다만 분실물 서비스는 매일 전체 사용자가 접속하는 서비스가 아니므로 실제 월간 활성 사용자는 약 5천~2만 명, 평일 일간 사용자는 약 300~1,500명, 피크 일간 사용자는 약 3천~8천 명 정도로 보는 것이 현실적이다. 동시 접속자는 평시 5~30명, 피크 50~200명 수준으로 가정한다.

이 정도 트래픽은 "처음부터 사용자가 있는 서비스"에는 해당하지만, DB 관점에서는 대규모 서비스라기보다 중소 규모 공공/학교 서비스에 가깝다. 이미지 파일은 S3에 저장하고 DB에는 객체 키와 메타데이터만 저장하므로 DB 부하는 목록 조회, 조건 검색, 상세 조회, 등록, 상태 변경, 관리자 처리 같은 비교적 일반적인 CRUD 중심으로 발생한다.

### 가격 비교

2026년 6월 1일 기준 AWS 서울 리전 가격을 기준으로 하면 RDS PostgreSQL Single-AZ의 온디맨드 인스턴스 비용은 다음과 같다.

| 항목 | 시간당 비용 | 월 730시간 기준 |
| --- | ---: | ---: |
| RDS PostgreSQL db.t4g.micro | $0.025 | 약 $18.25 |
| RDS PostgreSQL db.t4g.small | $0.051 | 약 $37.23 |
| RDS PostgreSQL db.t4g.medium | $0.102 | 약 $74.46 |
| Aurora PostgreSQL Serverless v2 | $0.20 / ACU-hour | 평균 0.5 ACU 기준 약 $73.00 |

스토리지는 RDS gp3가 약 $0.131/GB-month, Aurora 스토리지가 약 $0.120/GB-month 수준이다. 분실물 서비스는 이미지 원본을 S3에 저장하므로 DB 스토리지 비용 차이는 전체 판단을 뒤집을 정도로 크지 않다.

Aurora Serverless v2는 사용량에 따라 ACU 단위로 자동 확장된다는 장점이 있지만, 평균 0.5 ACU로만 운영되어도 월 컴퓨트 비용이 약 $73로 RDS db.t4g.medium과 거의 비슷하다. RDS db.t4g.small과 비교하면 거의 2배 수준이다. 즉 이 서비스처럼 상시 접속 가능한 웹서비스에서는 Aurora Serverless가 자동 확장된다는 이유만으로 비용 효율적이라고 보기 어렵다.

### Aurora Serverless v2가 유리해지는 조건

Aurora Serverless v2는 다음 조건이 명확할 때 설득력이 있다.

- 평시와 피크의 DB 부하 차이가 매우 크다.
- 피크가 예측하기 어렵고, 고정 인스턴스 크기를 정하기 어렵다.
- 피크 시간 외에는 DB가 거의 유휴 상태가 된다.
- 0 ACU auto-pause가 실제로 자주 발생할 만큼 연결이 끊기는 시간이 길다.
- RDS db.t4g.medium 또는 그 이상을 항상 켜두는 것보다 평균 ACU 비용이 낮다는 측정 결과가 있다.

하지만 성북구 7개 대학 분실물 시스템은 공용 서비스이므로 사용자가 언제든 검색하거나 문의할 수 있다. 백엔드 connection pool 또는 RDS Proxy가 연결을 유지하면 auto-pause 효과도 제한될 수 있다. 또한 분실물 시스템의 피크는 학기 초, 시험 기간, 축제 기간 등에 증가할 수 있지만, DB가 수십 배로 확장되어야 할 정도의 연산 중심 서비스는 아니다.

따라서 현재 시나리오에서는 RDS PostgreSQL db.t4g.small 또는 db.t4g.medium으로 시작하는 편이 비용과 운영 안정성의 균형이 좋다. 발표나 설계 문서에서는 실서비스 가정을 고려해 db.t4g.medium을 기본안으로 두고, 비용 절감이 더 중요하면 db.t4g.small부터 시작하는 선택지를 둘 수 있다.

### 팀원 의견에 대한 판단 기준

Aurora Serverless v2를 선택하기 위한 근거가 "자동 복구", "데이터 유실 방지", "관리형 DB라서 안전함"이라면 설득력이 약하다. RDS PostgreSQL도 자동 백업, 스냅샷, point-in-time recovery, Multi-AZ 배포, 장애 감지와 failover 같은 관리형 DB 기능을 제공한다. 즉 EC2 내부 Docker 볼륨에 DB를 두는 것과 비교하면 RDS만으로도 데이터 유실 위험과 복구 부담은 크게 줄어든다.

Aurora Serverless를 선택하려면 근거가 "복구가 된다"가 아니라 "트래픽 변동성이 커서 고정 인스턴스보다 평균 비용이나 운영 부담이 낮다"여야 한다. 예를 들어 실제 운영 지표에서 평시는 0.5 ACU 이하로 충분하지만 특정 기간에는 4~8 ACU 이상이 필요하고, 그 피크가 짧고 불규칙하다는 데이터가 있어야 한다. 또는 향후 전국 대학 확장처럼 수요 예측이 어렵고 빠른 확장이 중요한 상황이라면 Aurora Serverless가 대안이 될 수 있다.

결론적으로 현재 V2의 DB 선택은 RDS PostgreSQL이 더 타당하다. Aurora Serverless v2는 기술적으로 가능한 선택지이지만, 현재 규모와 비용 구조에서는 "초기 기본안"보다 "확장 단계에서 재검토할 대안"으로 남기는 것이 합리적이다.
